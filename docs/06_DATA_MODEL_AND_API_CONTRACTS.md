# 06 — Data Model, State Machines, and API Contracts

> Exact shapes. The builder AI must implement these names verbatim (tables, columns, enums, routes, error codes).
> ORM: **Drizzle** (`packages/core/src/db/schema.ts`). Database: **Postgres on Neon**.
> All timestamps `timestamptz` in UTC. All ids are prefixed strings generated by `newId(prefix)` (see §1).

---

## 1. Conventions

- **IDs:** `newId("inc")` → `inc_` + 20-char nanoid (alphabet `0-9a-z`). Prefixes: `ws`, `svc`, `ghi` (github installation row), `vcn` (vercel connection), `alr`, `inc`, `sus`, `ana`, `act`, `prb`, `evt`, `mck` (mcp key), `aic` (ai credential). Better Auth tables keep their own ids.
- **Tenancy:** every domain table has `workspace_id text not null`. Every query in `packages/core/src/repo/*` takes `workspaceId` as the **first argument** and filters by it. There is no repo function without it (except alert intake, which resolves the workspace from the service id, and GitHub webhooks, which resolve it from `installation_id`).
- **Secrets:** sealed columns use the 4-column pattern `<name>_ciphertext, <name>_iv, <name>_auth_tag, <name>_key_version` (see doc 07 §3.2).
- **Soft delete:** only `services.archived_at`. Everything else is hard delete or immutable.
- **Money/time:** no floats for anything persisted except `suspects.score` (`real`, display only).

## 3. State machines (implement as pure functions in `packages/core/src/domain/state.ts`)

### 3.1 IncidentStatus

```
open ──trace done──► triaged ──action proposed──► awaiting_approval ──approved──► mitigating ──vercel ok──► verifying ──3 healthy──► resolved
  │                     ▲                                │                             │                         │
  │                     └──── rejected / expired ────────┘                             └──── error ──────────────┴──► mitigation_failed
  └──► dismissed (user, from any non-terminal state)          resolved (manual "Mark resolved", from any non-terminal state)
```

| From | Event | To |
|---|---|---|
| open | `trace_ready` with good deployment | triaged → (propose) awaiting_approval |
| open | `trace_ready` without good deployment / `trace_failed` | triaged |
| triaged | `action_proposed` | awaiting_approval |
| awaiting_approval | `action_rejected` / `action_expired` / `action_cancelled` | triaged |
| awaiting_approval | `action_approved` | mitigating |
| mitigating | `approval_dispatch_failed` (could not send `action/approved`; approval undone) | awaiting_approval |
| mitigating | `action_cancelled` (drift / preflight failed at execution time) | triaged |
| mitigating | `action_executed` | verifying |
| mitigating | `action_failed` | mitigation_failed |
| verifying | `verified` | resolved (`closed_reason='verified'`) |
| verifying | `verification_failed` | mitigation_failed |
| mitigation_failed | `action_proposed` (user retries) | awaiting_approval |
| any non-terminal | `manual_resolve` | resolved (`closed_reason='manual'`) |
| any non-terminal | `dismiss` | dismissed |

Terminal: `resolved`, `dismissed`. `transitionIncident(current, event)` returns the next status or throws `InvalidTransitionError`. Persist with **compare-and-set**: `update incidents set status=$next where id=$id and status=$current returning id` — 0 rows → reload and re-evaluate (another worker won).

### 3.2 ActionStatus

```
proposed ─preflight ok─► awaiting_approval ─approve─► approved ─CAS─► executing ─vercel ok─► verifying ─► verified
    │                         │   │                                     │                       └────► verification_failed
    └─preflight fail─► cancelled  ├─reject─► rejected                   └─error─► failed
                              ├─timeout─► expired
                              └─drift─► cancelled
```

Terminal: `verified`, `verification_failed`, `failed`, `rejected`, `expired`, `cancelled`.

| From | Event | To |
|---|---|---|
| (insert) | preflight ok at proposal | awaiting_approval |
| (insert) | blocking preflight failure at proposal | cancelled |
| awaiting_approval | approve (CAS, not expired) | approved |
| awaiting_approval | reject | rejected |
| awaiting_approval | expiry (`expires_at <= now`) | expired |
| awaiting_approval | incident manually resolved/dismissed | cancelled |
| approved | dispatch of `action/approved` failed | awaiting_approval |
| approved | blocking preflight failure at execution (drift) | cancelled |
| approved | execution starts (CAS) | executing |
| executing | Vercel rejected / unauthorized / plan limit / job failed / confirm timeout | failed |
| executing | production confirmed on target | verifying |
| verifying | `VERIFY_REQUIRED_STREAK` consecutive healthy probes | verified |
| verifying | `VERIFY_MAX_PROBES` reached without streak | verification_failed |

`proposed` is reserved (rows are inserted directly as `awaiting_approval` or `cancelled` in the MVP); keep it in the enum and the partial index for forward compatibility.

## 4. Alert intake contract

`POST /api/v1/alerts/{serviceId}` — public, authenticated by HMAC only.

Headers:
- `x-firebreak-timestamp`: unix seconds. Reject if `|now - ts| > 300`.
- `x-firebreak-signature`: `v1=<hex>` where `hex = HMAC_SHA256(serviceAlertSecret, `${timestamp}.${rawBody}`)`. The HMAC key is the **full secret string as UTF-8 bytes, including the `whsec_` prefix — no base64 decoding** (unlike Stripe/Svix). Compare with `crypto.timingSafeEqual` on equal-length buffers.
- Body ≤ 64 KB (reject 413).

Body (Zod `AlertPayloadSchema`):
```ts
z.object({
  id: z.string().max(200).optional(),                       // sender's id → idempotency
  fingerprint: z.string().min(1).max(200),
  title: z.string().min(1).max(200),
  severity: z.enum(["critical", "high", "medium", "low"]).default("high"),
  source: z.string().max(50).default("webhook"),
  occurredAt: z.string().datetime().optional(),
  error: z.object({
    type: z.string().max(100).optional(),
    message: z.string().max(2000).optional(),
    frames: z.array(z.object({
      file: z.string().max(500),
      line: z.number().int().nullable().optional(),
      function: z.string().max(200).nullable().optional(),
      source: z.enum(["stack", "hint"]).default("stack"),
    })).max(30).default([]),
  }).default({ frames: [] }),
  observed: z.object({ url: z.string().url().optional(), status: z.number().int().optional(), sha: z.string().max(64).optional() }).optional(),
})
```

Responses:
| Status | Body | When |
|---|---|---|
| 202 | `{ data: { alertId, incidentId, deduped: boolean } }` | accepted |
| 200 | same, `deduped: true` | same `id` already received (idempotent replay) |
| 401 | `{ error: { code: "INVALID_SIGNATURE" } }` | bad/missing signature or stale timestamp (same body for all, no detail leak) |
| 404 | `{ error: { code: "NOT_FOUND" } }` | unknown or archived service |
| 413 / 422 / 429 | `PAYLOAD_TOO_LARGE` / `VALIDATION_FAILED` / `RATE_LIMITED` | |

Processing (must finish < 1 s; heavy work goes to Inngest):
1. Read raw body as text **before** JSON parse (signature is over raw bytes).
2. Load service (+ decrypt secret), verify signature, then parse + validate.
3. Rate-limit (60/min/service).
4. Insert alert. Find active incident by `(service_id, fingerprint)`; if found → attach (`alert_count+1`, `last_alert_at`, severity max), timeline `alert_deduped`, return. If not → allocate number, insert incident `status='open'`; on unique-violation of the partial index (race) → re-select and attach.
5. `inngest.send({ name: "incident/opened", data: { incidentId, workspaceId } })` only for new incidents.

## 5. Internal REST API (web app, session-authenticated)

Base `/api/v1`. Auth = Better Auth session cookie. Every handler: `const { user, workspace } = await requireSession(req)` → 401 if none.
Envelope: success `{ data: … }`; error `{ error: { code, message, details? } }`.

| Code | HTTP | Meaning |
|---|---|---|
| UNAUTHENTICATED | 401 | no/expired session |
| FORBIDDEN | 403 | wrong workspace / missing MCP scope |
| NOT_FOUND | 404 | (also used for other-workspace ids — never reveal existence) |
| VALIDATION_FAILED | 422 | Zod error; `details` = flattened issues |
| CONFLICT | 409 | invalid state transition, duplicate |
| PRECONDITION_FAILED | 412 | preflight failed (details = checks) |
| RATE_LIMITED | 429 | |
| UPSTREAM_ERROR | 502 | GitHub/Vercel/AI provider failed; `details.provider` |
| INTERNAL | 500 | unexpected; log with request id |
| INVALID_SIGNATURE | 401 | alert intake only (bad/missing/stale signature) |
| PAYLOAD_TOO_LARGE | 413 | alert intake only (> 64 KB) |

These 11 are the **only** top-level codes. Domain sub-codes go in `error.details.reason` (UI maps them to copy, doc 09 §6): `ACTION_EXPIRED`, `INVALID_STATE`, `NO_ROLLBACK_TARGET`, `TRACE_IN_PROGRESS`, `ANALYSIS_ATTEMPTS_EXHAUSTED`, `DISPATCH_FAILED`, `INSTALLATION_CLAIMED`, `INSTALLATION_NOT_ACCESSIBLE`, `VERCEL_TOKEN_REJECTED`, `VERCEL_UNAUTHORIZED`, `VERCEL_PLAN_LIMIT`, `VERCEL_REJECTED`, `VERCEL_CONFLICT`, `VERCEL_NOT_FOUND`, `VERCEL_UNAVAILABLE`, `GITHUB_FORBIDDEN`, `GITHUB_NOT_FOUND`, `GITHUB_UNAVAILABLE`, `SSRF_BLOCKED`, `QUOTA_EXCEEDED`, `MISSING_SCOPE`.

## 6. Validation & safety rules for all handlers

- Validate every body/query with Zod; unknown keys stripped.
- **SSRF guard** for `health_url` and `/services/health-check`: `https:` only in production; resolve DNS and reject private/loopback/link-local ranges (`10/8`, `172.16/12`, `192.168/16`, `127/8`, `169.254/16`, `::1`, `fc00::/7`, `fe80::/10`); no redirects followed (`redirect: "manual"`); 5 s timeout; read at most 64 KB of body.
- Never return sealed columns. Repo functions return DTOs, not raw rows.
- Every mutating route writes a timeline event when it concerns an incident.
- Request id: generate `x-request-id` if absent; include in logs and error bodies (`error.requestId`).
